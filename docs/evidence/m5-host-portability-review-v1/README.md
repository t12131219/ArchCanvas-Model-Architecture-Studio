# M5 host portability review v1

Date: 2026-10-07. This is a read-only portability and host-discovery audit. It does not promote any host to end-to-end `passed` and does not change the frozen `0.1.0-beta.1` archive.

The independent unpack directory was `/tmp/archcanvas-beta1-final-mf36q8x4/release`, created by the previously recorded bundle verification. The archive SHA-256 was `2c44459c195540fd3ac99a0fa7f52583090d85eae47b26fea4a64d1da85ff9ff`. All 41 relative Markdown links in `skills/archcanvas` were resolved from the unpacked Skill tree: 20 targets are present in the archive and 21 targets are historical M4 evidence files deliberately omitted from the local preview inventory. The omitted targets are not runtime imports, but a Skill reader opening those links outside the development checkout receives a missing file. A host installer should keep the Skill entry self-contained or replace those historical links with release-local evidence links; it must not silently rely on the development repository.

The formal source uses `Path(__file__).resolve()` to find its project root and then locates `src`, `fixtures`, and `studio/dist` relative to that root. The checked unpack layout therefore retains static source analysis and the bundled Studio path when invoked with explicit `PYTHONPATH`. The release does not contain Python or Node dependencies. PDF/PNG export needs the selected interpreter's publication converter and Cairo; SVG can use the TypeScript source through Node. A host launcher must pin the unpacked release root, use a data directory outside the immutable release, and set `-B`/`PYTHONDONTWRITEBYTECODE` (or equivalent) before running commands. `verify_directory()` rejects added `__pycache__` files and rejects an installed release whose inventory changes. The default service data directory would otherwise be under the release root and can make a verified install fail on the next activation check.

Codex CLI `0.160.0` was checked with `--help`, `--version`, `mcp list`, `features list`, `plugin --help`, and `debug models`; none invokes a model. The generated local app-server schema (`codex app-server generate-json-schema --out /tmp/archcanvas-codex-schema-audit`) exposes `initialize`, `skills/list`, and `skills/extraRoots/set`. The dedicated probe [probe_codex_skills.py](probe_codex_skills.py) starts a separate stdio app-server, sends only `initialize`, `initialized`, and `skills/list` with `forceReload`, then terminates that process. In a release directory with no project Skill installation, the real app-server returned an empty `archcanvasRows` list and no discovery errors; see [codex-baseline-escalated](codex-baseline-escalated/receipt.json). The sandbox-only attempt is retained in [codex-baseline-no-project-install](codex-baseline-no-project-install/receipt.json) and failed before protocol exchange because the CLI could not create its normal alias/cache state under the read-only sandbox. No model request, thread, turn, Skill write, credential read, or global Skill installation was requested by the probe.

The first installer draft was deliberately rejected by the exact-path probe because its embedded full release created two discovered `archcanvas` rows. The corrected installer filters the embedded `skills/archcanvas` subtree and records `embeddedSkillExcluded` in its local contract. The current readback is recorded below; the earlier v3 run remains as historical debugging evidence. These smoke checks use an explicitly staged local workspace and loopback service; they are package portability evidence, not a real Codex client workflow.

An exact metadata row proves discovery and frontmatter parsing only. It does not prove prompt-body execution, Studio browser editing, save/reopen, or export in a real Codex client. The M5 host matrix remains `not-tested` until those operations have their own host receipts.
