# 源码展开后的计算连续性与通用布线修复（2026-10-29）

本报告的连线修复与批量验收基于 **native-semantic/22**。当前 renderer 24 在此基础上将局部原子展开对齐“全部展开”的源码形态，并提供彩色方块／语义图标切换，见 [后续验收记录](node-atomic-menu-and-hierarchy-20261029.md)。纯调用名称语法移入源码详情，主画布保留原始计算调用及真实依赖；此前 renderer 21 的说明框方案已被替代。

参数读取箭头的后续通用呈现调整见 [2026-10-30 记录](parameter-dependency-presentation-20261030.md)，当前 renderer 25 将这类依赖放入节点详情。

## 为什么箭头接上了，整体数据流仍不连续

样例源码是 `x = torch.acos(x)`。该处已有语义事实是 `tanh → torch.acos(x) → mult`，其中 `torch` 是命名空间表达式，实际调用是 `torch.acos(x)`。静态分析保留了输入操作数、调用目标、输出及未解析边界；补视图卡片没有把该外部调用认证为已解析或已执行。

问题发生在语义到视图的投影：Agent 补充的 `torch`、`torch.acos` 源码检查卡片以原 opaque 调用为父节点；旧渲染器把“存在可见子节点”统一解释为“该计算节点展开为容器”。于是原调用自身不再有独立的计算图元，实际数据边停在容器边界，内部只有语法依赖。renderer 19 让这些紫色语法箭头连续，但语法依赖无法填补计算边界内部的张量路径。

因此，自适应生成图元不等于已经正确区分了计算、语法说明和容器接口。这是通用展开规则缺少分类，不是该处输入/输出从 IR 丢失，也不应把张量接入命名空间 `torch` 来掩盖它。

## 通用修复

旧图中的两个紫色箭头分别表示 receiver → callable、callable → 原调用，它们属于 Python 名称语法依赖。两个箭头各自落在说明框的不同边界，没有经过同一个图形端口，因此看起来仍然断开；即便强行连成一条，也不代表张量经过命名空间。前一轮增加说明框解决了计算端点被容器替代的问题，但仍把低价值语法放在主画布，造成重复和误读。

现在按已验证语法元数据处理：opaque 调用的 `sourceRulePath[0] === "func"` 子树仅由 SourceCall / SourceExpression 构成、且所有关联边均为明确 syntaxOnly 的 source-inspection 时，移为实际调用的详情附件。无名称、模型或项目匹配。带真实计算依赖的子树不隐藏；循环、分支、语句及无法确认用途的结构继续保留在画布。

`torch.acos` 原始调用保留自己的 ID、输入和输出，画面可沿实线阅读 `tanh → torch.acos → mult`。重复的名称说明框、`torch` 名称空间卡片及两条紫色语法箭头不再显示；它们的原始证据、节点和边仍保留在 canonical IR，并在节点/边 attached 核算和所选对象源码详情中逐项记录。未知调用继续保持未解析状态。本次没有新增解析或执行认证。

纯语法不再出现在层级展开导航中，避免点击展开又出现重复模块。受影响的旧布局重新生成，原布局保留为迁移来源；不受影响的旧概览布局继续保留。保存、重开及编辑副本保持源事实不变。

布线方面有三项独立的通用问题及修复：

- 源码布局将没有前驱的属性/资源读取节点留在起始层，造成跨整张图的长线。当前将非 mutable、无输入且仅有读取用途的资源节点画在首个消费者附近；写入、控制或 mutable 关系保留保守安排。这只改变位置，不推断执行顺序或复制资源。
- 旧默认可见性格点上限为 20,000，复杂合法通道会因为搜索规模过大而被当成局部失败。默认改为 80,000，未解边还有受限的较大搜索候选；同一批剩余预算允许中小图的 pending 边再尝试完整搜索。
- 原先一律 8 秒的默认批预算不足以覆盖较复杂的源码切面。当前按可见依赖规模分配 8–16 秒预算，完整搜索也遵守截止时间，显式传入的预算仍优先。耗尽时仍明确报告 pending，不能把未完成路径当作通过。

**没有 TFB、模型名称、模块名称或样例节点 ID 的运行时分支。TFB 仅作为只读黑盒验收数据，未执行、修改其源码；本次使用既有记录包。** 通用资源布局另有独立的人工构造图回归，包含 mutable 排除检查。
